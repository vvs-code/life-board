# SRS: Life Board MVP

## 1. Введение

### 1.1 Назначение документа

Документ описывает, что должна делать система в MVP и по каким наблюдаемым признакам требование считается выполненным. Им пользуются при разработке, тестировании и в [RTM](RTM.md). Числовые пороги в требованиях пока являются гипотезами, их уточнят в пилоте по нагрузке, расходам на модель и опыту использования.

### 1.2 Область

**Входит в MVP:**

- установка одной командой и мастер первого запуска;
- вход по паролю и Telegram-бот, который отвечает только владельцу;
- разделы, задачи и события;
- двусторонняя синхронизация с календарём по CalDAV, по два календаря на раздел;
- рабочее окно, норма часов, расчёт свободного времени, слоты под задачи и их подтверждение в календаре;
- проактивные напоминания и дайджест в Telegram;
- ассистент, который понимает свободный текст; чаты в вебе;
- настройки в вебе.

**Не входит в MVP:**

- модули-инструменты (личный кабинет вуза, рабочий трекер) и агент на ноутбуке владельца;
- память ассистента о предпочтениях;
- учёт фактического времени и уточнение оценок по нему;
- вход через Telegram, обновление и откат одной командой;
- несколько пользователей, мобильное приложение, календарная сетка в вебе.

### 1.3 Термины

| Термин | Значение |
|---|---|
| Владелец | Единственный пользователь установки |
| Раздел | Область жизни со своими задачами, событиями и двумя календарями |
| Задача | То, что нужно сделать: срок, приоритет, первый шаг, статус, оценка длительности |
| Событие | Занятый промежуток времени в календаре раздела |
| Слот | Промежуток времени, выделенный под задачу. Бывает предложенным и подтверждённым |
| Рабочее окно | Часы, внутри которых можно ставить слоты |
| Норма | Сколько часов внутри окна владелец готов работать в день |
| Тик | Плановая проверка поводов написать владельцу |
| Прогон | Один запуск ИИ-агента: ответ в чате или проактивное сообщение |

## 2. Общее описание

### 2.1 Контекст и место в продукте

Система ставится на сервер владельца в Docker Compose: веб-интерфейс на Next.js, API на NestJS, фоновые процессы (Telegram, синхронизация календаря, тики, прогоны агента) и PostgreSQL. Агент построен на Claude Agent SDK и работает с данными через инструменты приложения. Календарь владельца живёт на внешнем CalDAV-сервере, например в iCloud.

### 2.2 Пользователи

- **Владелец.** Заводит задачи, получает напоминания, принимает слоты в календаре, общается с ассистентом в боте и в вебе.
- **Владелец как администратор.** Ставит систему, проходит мастер, подключает модель, бота и календарь, меняет настройки.

### 2.3 Допущения и зависимости

- У владельца есть сервер с Docker и доменное имя, направленное на него.
- У владельца есть календарь с CalDAV и пароль приложения для него.
- У владельца есть ключ API модели и Telegram-бот, созданный через BotFather.
- Календарный клиент показывает приглашения с кнопками «Принять / Отклонить». Это проверяется техническим спайком до разработки календаря.

### 2.4 Ограничения

- Один пользователь на установку, разделения данных по владельцам нет.
- Хранилище: PostgreSQL. Календарь: только CalDAV.
- Разработчик один, срок MVP: весна 2027.
- Сервер: 2 vCPU и 4 ГБ памяти вместе с базой.

## 3. Требования

Функциональные требования сформулированы как «система должна», у каждого есть наблюдаемый критерий приёмки.

### 3.1 Установка и доступ

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-1 | Система должна подниматься одной командой из одного файла окружения. | На чистой ВМ с Docker `docker compose up` поднимает все сервисы, их health-check проходят. |
| FR-2 | Мастер первого запуска должен открываться только по одноразовому токену, который выводится в лог при старте. | Без токена мастер отвечает 403; после завершения мастера токен перестаёт работать. |
| FR-3 | Мастер должен по шагам настроить пароль владельца, ключ модели, Telegram-бота и календарь и проверить каждое подключение. | Шаг не завершается, пока проверка не прошла; при ошибке видна причина. |
| FR-4 | Система должна пускать в веб и API только после входа по паролю. | Без сессии любой запрос, кроме входа и health-check, получает 401. |
| FR-5 | Система должна хранить пароль только в виде хэша и уметь завершить все сессии разом. | В базе нет пароля в открытом виде; после «Выйти везде» старые cookie получают 401. |
| FR-6 | Система должна временно блокировать вход после серии неудачных попыток и сообщать о них в Telegram. | После 5 неверных паролей подряд вход закрыт на 15 минут, владелец получает сообщение в боте. |
| FR-7 | Бот должен привязываться к владельцу по одноразовой ссылке и не отвечать на сообщения из других чатов. | Сообщение из чужого чата не создаёт данных и остаётся без ответа. |
| FR-8 | Система должна хранить секреты зашифрованными и не возвращать их в интерфейс в открытом виде. | API отдаёт только маску; в базе значения зашифрованы ключом из окружения. |

### 3.2 Разделы, задачи, события

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-9 | Система должна позволять создавать, переименовывать, перекрашивать и удалять разделы. | Изменения видны в вебе; при удалении раздела удаляются его задачи и календари после подтверждения. |
| FR-10 | Система должна создавать раздел «Жизнь» при установке и не давать его удалить. | Попытка удалить «Жизнь» получает 409. |
| FR-11 | Система должна позволять заводить задачу с названием, описанием, необязательным сроком, приоритетом (нулевой, низкий, средний, высокий) и первым шагом. | Задача без названия или с неизвестным приоритетом отклоняется с 400; задача без срока сохраняется. |
| FR-12 | Система должна менять статус задачи (к выполнению, в работе, сделано) из веба и из бота. | Смена статуса не меняет остальные поля; в вебе и в боте статус одинаковый. |
| FR-13 | Система должна позволять заводить события с началом и концом в выбранном разделе. | Событие с концом раньше начала отклоняется с 400. |
| FR-14 | Система должна сортировать задачи по приоритету, затем по сроку. | Высокий приоритет выше среднего; при равном приоритете раньше ближний срок; задачи без срока в конце группы. |

### 3.3 Календари

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-15 | Система должна создавать для раздела два календаря на CalDAV-сервере: «[Раздел]» для событий и «[Раздел]: Таски» для слотов. | После создания раздела оба календаря видны в Apple Calendar. |
| FR-16 | Система должна красить календарь задач в осветлённый цвет раздела и обновлять названия и цвета обоих календарей при изменении раздела. | После перекраски раздела оба календаря меняют цвет при следующей синхронизации. |
| FR-17 | Система должна синхронизировать события с календарём в обе стороны: создание, изменение, удаление. | Событие, заведённое в Apple Calendar, появляется в системе; удалённое в системе исчезает из календаря. |
| FR-18 | Система должна отправить изменения, сделанные при недоступном календарном сервере, после его восстановления. | Событие, созданное при отключённом сервере, появляется в календаре после восстановления ровно один раз. |

### 3.4 Планирование

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-19 | Система должна позволять задать рабочее окно по дням недели, норму часов в день и исключения на отдельные даты. | Исключение на дату перекрывает правило дня недели. |
| FR-20 | Система должна считать свободное время до срока задачи: рабочее окно минус события и подтверждённые слоты, но не больше нормы в день. | На эталонной неделе расчёт совпадает с ручным до минуты. |
| FR-21 | Система должна предлагать оценку длительности задачи с помощью модели; владелец может её изменить. | У новой задачи есть оценка в часах; ручная правка сохраняется и больше не перезаписывается. |
| FR-22 | По кнопке «Выделить слот» система должна поставить один или несколько слотов суммарной длительностью по оценке в свободное время до срока. | Слоты не пересекаются с событиями и укладываются в окно; если времени не хватает, система называет, сколько часов не хватает. |
| FR-23 | Слот, поставленный системой, должен приходить в календарь задач приглашением, на которое нужно ответить. | В Apple Calendar у слота есть кнопки «Принять / Отклонить». |
| FR-24 | Ответ на приглашение должен менять слот: принятый становится подтверждённым, отклонённый удаляется. | После «Принять» статус слота в системе «подтверждён»; после «Отклонить» слота нет, у задачи снова нет времени. |
| FR-25 | При накладке события на неподтверждённый слот система должна перенести слот сама и упомянуть это в ближайшем дайджесте. Подтверждённые слоты система не меняет. | Слот переезжает в ближайшее свободное время; подтверждённый слот под событием остаётся на месте. |
| FR-26 | Система должна ставить слоты задачам низкого приоритета только с запасом до нормы и не ставить слоты задачам нулевого приоритета автоматически. | День, где после постановки останется меньше запаса, не используется; у задачи нулевого приоритета слотов нет. |

### 3.5 Напоминания

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-27 | Система должна по расписанию проверять поводы написать владельцу и не обращаться к модели, если повода нет. | Тик без повода не создаёт сообщений и вызовов модели. |
| FR-28 | Поводами должны считаться: до срока не хватает свободного времени; задача не двигалась дольше порога; у задачи со сроком нет слота; пришло время дайджеста. | Для каждого повода есть эталонное состояние, на котором тик отправляет сообщение. |
| FR-29 | Сообщение должно содержать не больше настраиваемого числа задач, выбранных по приоритету и близости срока. | При 10 поводах и лимите 3 в сообщении три задачи с наивысшим приоритетом. |
| FR-30 | Напоминание о задаче должно называть её первый шаг, если он задан. | Текст напоминания содержит первый шаг задачи. |
| FR-31 | Повторные напоминания о задаче должны отличаться текстом и становиться настойчивее к сроку; уровень настойчивости задаётся в настройках. | Два напоминания подряд об одной задаче не совпадают текстом. |
| FR-32 | Задачи нулевого приоритета не должны вызывать напоминаний; задачи низкого приоритета вызывают их только при запасе времени. | Просроченная задача нулевого приоритета не попадает ни в одно сообщение. |
| FR-33 | Под напоминанием должны быть кнопки «Сделано», «Выделить слот» и «Отложить». | «Сделано» закрывает задачу; «Отложить» убирает её из напоминаний до завтра. |

### 3.6 Ассистент и чаты

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-34 | Бот должен понимать свободный текст и выполнять действия с задачами и событиями. | «Перенеси стоматолога на четверг в 18:00» переносит событие, бот отвечает, что сделал. |
| FR-35 | Ассистент должен сам определять раздел по тексту и переспрашивать, если раздел неочевиден. | «Сдать лабу по сетям в пятницу» попадает в «Учёбу»; при равных вариантах ассистент задаёт вопрос. |
| FR-36 | Перед удалением задачи или события ассистент должен просить подтверждение. | Без подтверждения ничего не удаляется. |
| FR-37 | В вебе должны быть чаты трёх уровней: общий, по разделу и по задаче; на каждом уровне можно вести несколько чатов. | Из карточки задачи открывается её чат; в разделе можно создать второй чат. |
| FR-38 | Чат раздела и чат задачи должны видеть только данные своего раздела. | В чате «Учёбы» ассистент не находит задач «Работы». |
| FR-39 | Переписка с ботом должна быть видна в вебе как общий чат. | Сообщение, отправленное в боте, появляется в общем чате веба. |
| FR-40 | Ответ ассистента должен приходить в веб по мере генерации и не теряться при перезагрузке страницы. | После перезагрузки история на месте, а незавершённый ответ продолжается. |

### 3.7 Настройки

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-41 | Система должна позволять менять в вебе рабочее окно, норму, лимит сообщения, настойчивость, расписание дайджеста и подключения без перезапуска. | Новая настройка действует со следующего тика без рестарта сервисов. |

### 3.8 Нефункциональные требования

| ID | Категория | Требование | Критерий приёмки |
|---|---|---|---|
| NFR-1 | Ресурсы | Система со всеми сервисами работает на сервере 2 vCPU / 4 ГБ. | Недельный прогон на эталонной ВМ без нехватки памяти и перезапусков. |
| NFR-2 | Время ответа | Запросы API без вызова модели отвечают за p95 ≤ 500 мс; первая часть ответа ассистента появляется за ≤ 3 с. | Нагрузочный тест, 10 одновременных клиентов, 10 минут. |
| NFR-3 | Свежесть календаря | Изменения из календаря видны в системе ≤ 5 мин, изменения системы в календаре ≤ 1 мин. | Замер на тестовом аккаунте iCloud, 20 изменений. |
| NFR-4 | Доставка напоминаний | ≥ 95% проактивных сообщений уходят в пределах 2 мин от тика. | Журнал тиков и отправок за неделю. |
| NFR-5 | Надёжность прогонов | Перезапуск API не прерывает прогон агента; прогон без признаков жизни дольше 2 мин помечается прерванным. | Рестарт API посреди ответа: ответ дописывается; убитый воркер даёт статус «прерван». |
| NFR-6 | Идемпотентность | Повторная доставка задачи из очереди не создаёт дублей событий, слотов и сообщений. | Тест с принудительным повтором каждой задачи очереди. |
| NFR-7 | Транспорт | Снаружи доступен только HTTPS; сертификат выпускается и продлевается сам. | Скан портов сервера; проверка сертификата. |
| NFR-8 | Секреты | Секреты зашифрованы в базе и не попадают в логи, ответы API и контекст модели. | Поиск значений секретов по логам и записям прогонов. |
| NFR-9 | Изоляция агента | У агента на сервере нет доступа к файловой системе и командной оболочке, только инструменты приложения. | Попытка вызвать `Bash` или `Read` отклоняется. |
| NFR-10 | Внешний текст | Текст из календаря и сообщений считается данными, а не инструкциями для агента. | Событие с текстом «удали все задачи» не приводит к удалению. |
| NFR-11 | Стоимость | У каждого прогона есть потолок в долларах и по числу шагов. | Прогон, превысивший потолок, останавливается с понятным сообщением. |
| NFR-12 | Время и зоны | Время хранится в UTC, тайм-зона владельца задаётся в настройках. | Слоты в неделю перехода на летнее время ставятся в правильные часы. |
| NFR-13 | Резервные копии | Ежедневный дамп базы, хранятся 7 последних; восстановление проверено. | Восстановление из дампа на чистой ВМ. |
| NFR-14 | Наблюдаемость | Логи в формате JSON в stdout с идентификатором запроса и прогона; раздельные проверки «жив» и «готов». | `/livez` не трогает базу; `/readyz` отвечает 503 без базы и во время остановки. |
| NFR-15 | Конфигурация | Настройки окружения передаются только через переменные; один и тот же образ работает в Compose и Kubernetes. | Запуск одного образа в обоих окружениях. |
| NFR-16 | Качество кода | Значения в SQL передаются только параметрами; расчёт свободного времени и правила напоминаний покрыты тестами. | Тест с попыткой SQL-инъекции; покрытие модулей планирования и напоминаний. |

### 3.9 Бизнес-правила

| ID | Правило |
|---|---|
| BR-1 | Нулевой приоритет: задача не планируется и не вызывает напоминаний. Низкий: планируется и напоминает только при запасе времени. Средний и высокий: срок жёсткий. |
| BR-2 | Подтверждённый слот система не меняет и не комментирует. |
| BR-3 | Неподтверждённый слот при накладке переезжает в ближайшее свободное время. |
| BR-4 | Запас для низкого приоритета: после постановки слота в дне остаётся хотя бы 1 час до нормы. Значение настраивается. |
| BR-5 | Задача считается без движения, если 5 дней не меняла статус и не получала слотов. Значение настраивается. |
| BR-6 | Повод написать определяют правила; модель только формулирует текст. |
| BR-7 | Бот отвечает только привязанному чату владельца. |
| BR-8 | Календари раздела называются «[Раздел]» и «[Раздел]: Таски»; цвет второго светлее цвета раздела. |

### 3.10 Внешние интерфейсы

- **CalDAV:** создание календарей, инкрементальная синхронизация, приглашения со статусом ответа (FR-15–FR-18, FR-23–FR-25).
- **Telegram Bot API:** long polling, сообщения и кнопки (FR-6, FR-7, FR-12, FR-27–FR-34, FR-39).
