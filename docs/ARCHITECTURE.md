Статус: Draft · 0.4 · 23.10.2026. Цели в [PRD](PRD.md), требования в [SRS](SRS.md), трассировка в [RTM](RTM.md).

## 1. Стек и принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Язык | TypeScript везде | Один язык на фронт, бэк, воркеры и раннер |
| Фронтенд | Next.js (App Router) + Gravity UI | Донорские паттерны из solvehub |
| Бэкенд | NestJS + tRPC | Сквозная типизация без кодогенерации |
| БД | PostgreSQL + Prisma | jsonb, `LISTEN/NOTIFY`, тайм-зонные типы, pgvector на будущее |
| Пакетный менеджер | pnpm workspaces | Строгие workspace-зависимости |
| Агент | Claude Agent SDK | Агентный цикл, субагенты и MCP-клиент готовы |
| Очередь техзадач | pg-boss | Ретраи, visibility timeout, отложенный запуск |
| Модули | MCP-серверы | Открытый стандарт, сторонние подключаются без нашего кода |
| Календарь | CalDAV, двусторонний | Работает с Apple, Яндексом, Nextcloud |
| Telegram | long polling | Не требует публичного HTTPS для self-host |
| Раннер на машине | WebSocket, соединение исходящее | Работает за NAT, без проброса портов |

## 2. Структура репозитория

pnpm-монорепозиторий по образцу solvehub. Целевой стек лежит в корне, рабочий MVP-срез из домашних заданий — в `mvp/`.

```
frontend/              Next.js App Router + Gravity UI + tRPC, слои FSD
  app/                   страницы: сегодня, раздел, задача, чат, настройки, мастер, вход
  src/shared/api/        tRPC-клиент (тип роутера из backend), подписка на SSE
  src/entities/          task: строка задачи, приоритеты
  src/features/          allocate-slot: кнопка «Выделить слот»
  src/widgets/           today, chat
backend/               NestJS: tRPC для веба, SSE, WebSocket для раннеров
  src/trpc/              TrpcService (уровни доступа) и TrpcRouter (сборка модулей)
  src/modules/<имя>/     <имя>.router.ts без логики + <имя>.service.ts + <имя>.module.ts
workers/               фоновые процессы: Telegram, CalDAV, тики, агентные прогоны, pg-boss
modules/               встроенные MCP-модули, по папке на модуль с module.json
  browser/
  tracker/
runner/                раннер для рабочей машины, отдельный артефакт
packages/
  common/              zod-схемы, константы, протокол раннера, чистая логика планирования
  db/                  Prisma: схема и клиент
  nest-common/         общие Nest-модули: Prisma, конфиг, шифрование секретов, pg_notify, пробы
  agent/               сборка агента на Claude Agent SDK: субагенты разделов, доменные тулы
deploy/                compose.yaml, Caddyfile, Dockerfile'ы, install.sh, CLI lifeboard
mvp/                   MVP-срез: Express + PostgreSQL, Docker Compose, Kubernetes
docs/
```

`backend` и `workers` собираются в один образ (`deploy/Dockerfile.server`) с разными точками входа. Общие Nest-модули лежат в `packages/nest-common`, как в solvehub.

## 3. Процессы

```
┌─ сервер · docker compose ─────────────────────────────┐
│                                                       │
│  caddy ──┬─► frontend (Next.js)                       │
│          └─► backend (NestJS)                         │
│                 │  tRPC · SSE · WebSocket для раннеров│
│                 │                                     │
│              postgres ◄───────────────────────────────┤
│                 │  данные · pg-boss · LISTEN/NOTIFY   │
│                 │                                     │
│              workers (NestJS)                         │
│                 ├─ Telegram long polling              │
│                 ├─ cron: тики проактивности           │
│                 ├─ CalDAV sync                        │
│                 └─ агентные прогоны                   │
└───────────────────────────────────────────────────────┘
                        ▲
                        │ WebSocket, исходящее с машины
                        │
          ┌─ рабочая машина ──────────────┐
          │ runner                        │
          │  └─ агент + Read/Edit/Bash    │
          └───────────────────────────────┘
```

**Кто за что отвечает:**

- **frontend** — только отрисовка. В БД не ходит, всё через tRPC.
- **backend** — tRPC для веба, SSE-ретрансляция событий, WebSocket-эндпоинт для раннеров, постановка задач. **Агентов не запускает.**
- **workers** — всё, что идёт само и долго: Telegram, расписания, синхронизация, агентные прогоны.
- **runner** — агентные прогоны на рабочей машине, там где файлы.

## 4. Две очереди, по природе работы

**pg-boss — технические задачи.** Короткие, частые, пользователю не видны: синхронизировать календарь, прогнать тик проактивности, отправить сообщение в Telegram. Ретраи, backoff, отложенный запуск, дедупликация — из коробки. Живёт в своей схеме БД.

**`agent_run` — агентные прогоны.** Доменная сущность в нашей схеме, а не техническая очередь. Идёт минутами, видна в интерфейсе, имеет статус, отменяется и перезапускается кнопкой.

```
agent_run
  id
  kind          chat | proactive | machine
  chat_id       для kind=chat
  space_id
  task_id
  machine_id    для kind=machine
  status        queued | running | awaiting_approval | done | failed | cancelled | interrupted
  session_id    сессия Agent SDK
  cost_usd
  started_at, finished_at, heartbeat_at
```

Разбирается `SELECT ... FOR UPDATE SKIP LOCKED`. Прогон без свежего `heartbeat_at` считается брошенным и переводится в `interrupted`.

## 5. Доставка событий в интерфейс

Единый канал для всего, что происходит не по запросу пользователя.

```
источник события          →  postgres NOTIFY  →  backend  →  SSE  →  frontend
(workers / runner / bot)      канал chat:<id>     слушает      держит
                              или ui:events       LISTEN       соединение
```

Каждое сообщение агента сначала пишется в `message`, затем рассылается через `pg_notify`. Из этого следует:

- Веб переподключился — читает историю из БД и продолжает слушать. Ничего не теряется.
- `backend` перезапустился — прогон в `workers` не прерывается.
- Канал один и тот же для ответов агента, проактивных сообщений, результатов с машины и статуса синхронизации.

## 6. Сценарии запуска

### 6.1 Сообщение в чат из веба

```
frontend            backend             postgres          workers
   │ tRPC: send        │                   │                 │
   ├──────────────────►│                   │                 │
   │                   │ INSERT message    │                 │
   │                   ├──────────────────►│                 │
   │                   │ INSERT agent_run  │                 │
   │                   ├──────────────────►│                 │
   │ ◄─── run_id ──────┤                   │                 │
   │                   │                   │ SKIP LOCKED     │
   │ SSE подписка      │                   │◄────────────────┤
   ├──────────────────►│ LISTEN chat:<id>  │                 │
   │                   ├──────────────────►│   query() → CLI │
   │                   │                   │◄─ NOTIFY ───────┤
   │ ◄─── событие ─────┤                   │  (на каждое     │
   │ ◄─── событие ─────┤                   │   сообщение)    │
   │ ◄─── done ────────┤                   │◄─ NOTIFY ───────┤
```

Уровень чата определяет опции запуска:

| Чат | Опции Agent SDK |
|---|---|
| Общий | `agents: { life, study, work }`, делегирование по `description` |
| Раздел | `agent: "work"` — главный поток сразу раздел |
| Таска | `agent: "work"` + контекст таски в промпте, `task_id` по умолчанию в тулах |

Новое сообщение в существующем чате — `resume: session_id`. Ветвление чата — `forkSession: true`.

### 6.2 Сообщение в Telegram

```
workers: long polling получил апдейт
  → находит общий чат, привязанный к Telegram
  → INSERT message, INSERT agent_run (kind=chat)
  → тот же путь, что 6.1
  → ответ уходит и в Telegram, и в веб через NOTIFY
```

Телеграм-чат — обычный общий чат, просто с постоянной привязкой. В вебе виден наравне с остальными.

### 6.3 Тик проактивности

```
cron в workers (интервал из настроек)
  → pg-boss ставит задачу proactive_tick с ключом дедупликации
  → воркер считает ДЕТЕРМИНИРОВАННО:
      свободное время до каждого жёсткого дедлайна
      таски без слотов
      таски без движения дольше порога
      просроченные подтверждения
  → повода нет → выходим молча, ничего не пишем
  → повод есть → выбирает не больше N по приоритету
  → INSERT agent_run (kind=proactive)
  → агент формулирует текст с учётом памяти и истории проигноров
  → отправка в Telegram + NOTIFY в веб
```

Правила решают **есть ли повод**, модель решает **как сказать**. Молчание — штатный результат, и оно не стоит ни одного запроса к модели.

### 6.4 Синхронизация календаря

```
pg-boss по расписанию, на каждый календарь раздела
  → REPORT sync-collection с сохранённым sync-token
  → пришли изменения:
      внешнее событие         → upsert в events
      ответ на приглашение    → слот подтверждён/отклонён
      удаление                → мягкое удаление
  → наши изменения с прошлого раза → PUT/DELETE наружу
  → конфликт по ETag → перечитать и разрешить по правилам:
      неподтверждённый слот — двигаем молча
      подтверждённый        — не трогаем
  → сохранить новый sync-token
```

Два календаря на раздел: `[Раздел]` для событий, `[Раздел]: Таски` для слотов, цвет второго — осветлённый оттенок первого.

### 6.5 Задача на рабочей машине

```
runner                 backend              postgres           
   │ WS connect          │                     │               
   ├────────────────────►│ токен машины        │               
   │ hello{capacity:2}   │                     │               
   ├────────────────────►│ machine online      │               
   │                     ├────────────────────►│               
   │                     │                     │               
   │ ◄── task_assign ────┤◄── agent_run ───────┤ kind=machine  
   │                     │                     │               
   │ query() локально    │                     │               
   │  Read/Edit/Bash     │                     │               
   │                     │                     │               
   │ ─── run_event ─────►│ INSERT message      │               
   │                     ├────────► NOTIFY ────┤ → SSE в веб   
   │                     │                     │               
   │ ─── ask_approval ──►│ → Telegram кнопка   │               
   │ ◄── approval ───────┤ ← ответ             │               
   │                     │                     │               
   │ ─── run_done ──────►│ status=done         │               
```

Ключевые свойства:

- **Соединение исходящее.** Машина за NAT, в кафе, где угодно — проброс портов не нужен.
- **Машина выключена — задача ждёт.** Никаких таймаутов и ретраев сетевого вызова.
- **Параллелизм по ёмкости.** Раннер объявляет, сколько прогонов тянет; сервер не шлёт больше.
- **Разрыв соединения** — машина offline, её незавершённые прогоны в `interrupted`, видны в интерфейсе с кнопкой перезапуска.
- **`canUseTool`** перехватывает необратимые действия и уводит вопрос в Telegram.

### 6.6 Подключение модуля

```
старт backend → скан modules/*/module.json → каталог в памяти
пользователь в вебе → тумблер → форма из manifest.settings
  → секреты шифруются, INSERT module_instance
  → привязка к разделам
при сборке агента:
  агент раздела получает mcpServers = активные модули этого раздела
  allowedTools = mcp__<module>__*
```

Добавить встроенный модуль — положить папку с манифестом, появится в каталоге сам. Внешний сторонний MCP-сервер добавляется в вебе адресом или командой, без папки в репозитории.

## 7. Сборка агента

```ts
// packages/agent
const lifeboard = createSdkMcpServer({
  name: "lifeboard",
  tools: [createTask, findTasks, allocateSlot, moveEvent, remember, recall /* ... */],
});

query({
  prompt,
  options: {
    agent: "work",                       // для чата раздела и таски
    agents: { life, study, work },       // разделы как субагенты
    mcpServers: { lifeboard, ...spaceModules },
    allowedTools: ["mcp__lifeboard__*", "mcp__browser__*"],
    disallowedTools: ["Bash", "Write", "Edit", "Read", "Glob", "Grep", "WebFetch"],
    resume: chat.sessionId,
    maxBudgetUsd: settings.runBudget,
    maxTurns: settings.maxTurns,
    canUseTool,
    persistSession: false,
  },
});
```

**Встроенные тулы на сервере выключены явно.** Агенту в разделе «Жизнь» незачем уметь `Bash` на хосте. На раннере — наоборот, они и есть смысл.

Доменные тулы — in-process MCP-сервер: живёт в том же процессе, ходит в Prisma напрямую, отдельный процесс не нужен.

Тенантности нет: один пользователь, `owner_id` нигде не заводим. Переход к нескольким пользователям — миграция схемы, а не флаг. Зафиксировано осознанно.

## 9. Секреты

Инфраструктурные — в `.env`, только то, без чего процесс не стартует: строка подключения к БД, ключ шифрования, домен, версия. Все они записываются скриптом установки, руками не вводятся.

Всё остальное вводится в интерфейсе и лежит в БД зашифрованным (AES-256-GCM, ключ из `.env`): пароли CalDAV, ключ модели, токен бота, токены модулей, токены машин. Наружу секрет второй раз не отдаётся — только маска и кнопка «заменить».

Потеря ключа шифрования означает потерю всех сохранённых доступов. Данные при этом целы.

## 10. Развёртывание

### Принцип

**`.env` — машинный файл. Им владеет `lifeboard`, человек в него не ходит.** Всё, что требуется до старта веба, либо генерируется при установке, либо приходит аргументом команды. Всё остальное настраивается в мастере и в интерфейсе.

### Установка

```bash
curl -fsSL https://github.com/vvs-code/life-board/releases/latest/download/install.sh \
  | sh -s -- --domain life.veselov.dev
```

Скрипт лежит ассетом релиза, а не в ветке: так он согласован с `compose.yaml` того же релиза по построению. В README дублируется вариант «скачать, прочитать, запустить» для тех, кто не исполняет удалённые скрипты вслепую.

Что делает скрипт: тянет `compose.yaml` из релиза, генерирует ключ шифрования и пароль к базе, записывает домен и версию, кладёт на хост команду `lifeboard`, поднимает стек.

Флаги: `--local` — поднять на localhost без TLS и без домена, аргументов не требуется вообще; `--auto-update` — завести на хосте cron, дёргающий `lifeboard update` в тихое окно.

### Состав стека

```yaml
services:
  caddy:      # авто-TLS, единственный публичный вход
  frontend:
  backend:
  workers:    # применяет миграции при старте
  postgres:
```

Публично торчит только Caddy. Postgres — во внутренней сети, наружу не публикуется.

### Версии

Точная версия пинится в `.env` (`LIFEBOARD_VERSION=1.3.2`), записывает её `lifeboard`. Из четырёх вариантов — `latest`, мажорный тег, точная версия, digest — только точная версия даёт одновременно: видно текущее состояние, откат возможен, ничего не меняется без явного действия. Digest добавляется поверх позже lock-файлом, без переделки механики.

Образы — GHCR, пушатся из GitHub Actions.

### Миграции

Применяет `workers` при старте, автоматически, сняв дамп перед этим. Инстанс один, гонка стартов невозможна, а ручной шаг превращал бы обновление в двухходовку.

### Команды

```bash
lifeboard update          # дамп → pull → миграции → перезапуск
lifeboard rollback        # вернуть образ И дамп вместе
lifeboard backup          # дамп по требованию
lifeboard status          # что поднято, какая версия, что не в порядке
lifeboard logs            # хвост логов всех процессов
lifeboard set-domain      # сменить домен и перевыпустить сертификат
```

Откат образа сам по себе не откатывает схему БД, поэтому `rollback` возвращает образ и дамп вместе. Релизы с несовместимой миграцией помечаются в GitHub Release, `update` на таком предупреждает отдельно.

Приложение проверяет наличие новой версии и пишет в Telegram, что вышло и что изменилось.

### Чего сознательно нет

**Кнопки «Обновить» в интерфейсе.** Чтобы контейнер перезапустил сам себя, ему нужен `docker.sock`, то есть root на хосте. В системе живёт браузерный модуль, приносящий содержимое недоверенных страниц в контекст агента; промпт-инъекция плюс доступ к сокету даёт прямой побег на хост. Обновление остаётся командой на хосте, а автоматизация — хостовым cron, которому сокет не нужен.

### Бэкапы

Ежедневный дамп в volume, хранятся последние N. Перед каждым обновлением снимается отдельный дамп. Выгрузку наружу владелец настраивает сам — в поставку не входит.

### Раннер

Ставится на рабочую машину отдельной командой, в compose не входит. Токен машины выдаётся в интерфейсе.

## 12. Открытые вопросы

Помимо перечисленных в [PRD](PRD.md), в разделе о рисках:

1. **Версия Claude Code CLI в образе.** Agent SDK запускает CLI подпроцессом. Версию надо пинить и осознанно обновлять — поведение агента от неё зависит.
2. **Доступ к модели на сервере.** API-ключ обязателен. На раннере возможна подписка, потому что это личная машина владельца. Границу зафиксировать в документации, чтобы не расползлась.
3. **Первая установка раннера.** Как ставится, как получает токен, как обновляется. Тот же принцип «одна команда, руками в конфиг не лезем» должен работать и здесь.
4. **Тайм-зона и переходы на летнее время** в расчёте слотов и рабочего окна.
