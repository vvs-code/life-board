# Отчёт. Домашнее задание №1 — приложение 12 факторов

## Доменная область

**Life Board** — личная панель управления жизнью. Пользователь делит жизнь на разделы («Жизнь», «Учёба», «Работа»), заводит в них таски с дедлайном, приоритетом и статусом и ведёт их до выполнения.

В репозитории есть полное описание целевого продукта: [docs/PRD.md](../../PRD.md), [docs/SRS.md](../../SRS.md) и [docs/ARCHITECTURE.md](../../ARCHITECTURE.md). Это домашнее задание реализует его минимальный срез — разделы и таски с полным CRUD. На этой основе будут делаться следующие задания.

## Стек

| Слой | Технология |
|---|---|
| Фронтенд | Статичные HTML + JavaScript без сборки, отдаются nginx |
| Бэкенд | Node.js 22, Express, REST по HTTP/1.1 |
| СУБД | PostgreSQL 16, драйвер `pg` |
| Запуск | Docker, Docker Compose |

Стек выбран намеренно лёгким: два npm-пакета на бэкенде и ноль на фронтенде, образы на Alpine. Окружение поднимается быстро и не съедает ресурсы — это пригодится в следующих заданиях, в том числе для балансировки.

Nginx во фронтенд-контейнере отдаёт статику и проксирует `/api/*` на бэкенд. Браузер ходит только в один origin, поэтому CORS не нужен.

## Сущности

**Раздел (`spaces`)** — область жизни.

| Поле | Тип | Описание |
|---|---|---|
| `id` | serial | Идентификатор |
| `name` | text | Название |
| `color` | text | Цвет в интерфейсе |
| `created_at` | timestamptz | Время создания |

**Таска (`tasks`)** — то, что нужно сделать. Принадлежит разделу; при удалении раздела его таски удаляются каскадом.

| Поле | Тип | Описание |
|---|---|---|
| `id` | serial | Идентификатор |
| `space_id` | integer → `spaces.id` | Раздел |
| `title` | text | Что сделать |
| `description` | text | Подробности |
| `deadline` | timestamptz, nullable | Срок; таска может быть без срока |
| `priority` | `zero` / `low` / `mid` / `high` | Приоритет |
| `status` | `todo` / `in_progress` / `done` | Статус |
| `created_at` | timestamptz | Время создания |

### API

Для обеих сущностей реализован одинаковый CRUD:

| Метод | Путь | Действие |
|---|---|---|
| GET | `/api/spaces`, `/api/tasks` | Список (для тасок — фильтр `?space_id=`) |
| GET | `/api/{spaces,tasks}/:id` | Одна запись |
| POST | `/api/{spaces,tasks}` | Создание |
| PUT | `/api/{spaces,tasks}/:id` | Изменение |
| DELETE | `/api/{spaces,tasks}/:id` | Удаление |
| GET | `/health` | Проверка живости вместе с доступностью БД |

## Запуск

```bash
cp .env.example .env
docker compose up --build
```

Приложение откроется на http://localhost:8080. Миграции применяются автоматически отдельным одноразовым контейнером `migrate` перед стартом бэкенда.

## Соответствие 12 факторам

### I. Кодовая база

Одна кодовая база в одном git-репозитории. Из неё собираются все развёртывания; окружения отличаются только конфигурацией, а не кодом. Фронтенд и бэкенд лежат в одном репозитории как части одного приложения, а не как отдельные приложения с общим кодом.

### II. Зависимости

Зависимости бэкенда явно объявлены в `mvp/backend/package.json` и зафиксированы в `package-lock.json`. В образе они ставятся через `npm ci` — строго по lock-файлу, с воспроизводимым результатом. Неявных системных зависимостей нет: всё нужное — в базовом образе `node:22-alpine`. У фронтенда зависимостей нет, только образ `nginx:1.27-alpine` с зафиксированной версией.

### III. Конфигурация

Всё, что отличается между окружениями, задаётся переменными окружения:

- бэкенд: `DATABASE_URL`, `PORT` (`mvp/backend/src/config.js`). Без `DATABASE_URL` процесс сразу падает с понятной ошибкой, а не стартует с подставленным значением по умолчанию;
- фронтенд: `PORT` и `BACKEND_URL`. Nginx подставляет их в конфиг при старте контейнера через механизм шаблонов (`mvp/frontend/templates/default.conf.template`);
- Postgres: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`.

В коде нет ни паролей, ни адресов. `.env` исключён из git, в репозитории лежит только `.env.example`.

### IV. Сторонние службы

PostgreSQL — подключаемый ресурс, доступный только по URL из `DATABASE_URL`. Заменить локальный контейнер на управляемую базу у облачного провайдера можно, поменяв одну переменную, без изменения кода.

### V. Сборка, релиз, выполнение

Три стадии разделены:

- **сборка** — `docker build` превращает код в образ с установленными зависимостями;
- **релиз** — образ плюс конфигурация из окружения;
- **выполнение** — запуск контейнера из готового образа.

В рантайме код не меняется и зависимости не доустанавливаются. Миграции и бэкенд используют один и тот же образ.

### VI. Процессы

Бэкенд stateless: между запросами в памяти процесса ничего не хранится, всё состояние — в Postgres. Сессий, локальных файлов и кешей нет. Поэтому можно поднять несколько экземпляров бэкенда за балансировщиком — это пригодится в задании про балансировку трафика.

### VII. Привязка портов

Каждый сервис сам слушает порт из переменной окружения: бэкенд — Express на `PORT`, фронтенд — nginx на `PORT`. Внешний веб-сервер, в который приложение пришлось бы «встраивать», не нужен. Наружу публикуется только порт фронтенда (`APP_PORT`), бэкенд и база доступны лишь во внутренней сети compose.

### VIII. Параллелизм

Масштабирование — запуском дополнительных процессов, а не наращиванием одного. Типы процессов разделены: `backend` обслуживает HTTP, `migrate` выполняет разовую работу. Бэкенд масштабируется горизонтально: `docker compose up --scale backend=3`. Это возможно благодаря фактору VI.

### IX. Утилизируемость

Процессы быстро стартуют — секунды — и корректно завершаются. Бэкенд по `SIGTERM` перестаёт принимать новые соединения, дожидается текущих запросов и закрывает пул соединений с базой (`mvp/backend/src/index.js`). Миграция выполняется в транзакции, поэтому прерванный процесс не оставляет базу в промежуточном состоянии. У `backend` и `frontend` есть healthcheck'и: фронтенд стартует только после того, как бэкенд ответил на `/health`, а он проверяет и сам процесс, и доступность базы.

### X. Паритет разработки и эксплуатации

Локально и в эксплуатации используются одни и те же образы, одна версия Postgres, один `mvp/compose.yaml`. Нет ситуации «локально SQLite, в проде Postgres». Разработчику нужен только Docker.

### XI. Журналирование

Приложение пишет логи в stdout как поток событий — по одному JSON-объекту на строку с временем, уровнем и полями запроса (`mvp/backend/src/log.js`). Файлов логов и ротации внутри приложения нет; сбором и хранением занимается окружение — в `mvp/compose.yaml` Docker хранит поток с ограничением размера (драйвер `local`, общий якорь `x-logging`). Посмотреть логи: `docker compose logs -f backend`.

### XII. Задачи администрирования

Миграции схемы — разовый административный процесс: отдельный сервис `migrate` в `mvp/compose.yaml`, который запускается из того же образа и с той же конфигурацией, что и бэкенд, отрабатывает и завершается. Применённые миграции учитываются в таблице `schema_migrations`, повторный запуск безопасен. Запустить вручную: `docker compose run --rm migrate`.
