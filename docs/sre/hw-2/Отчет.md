# Отчёт. Домашнее задание №2 — запуск в Kubernetes (minikube)

Приложение то же, что в ДЗ №1: **Life Board** — разделы и таски с CRUD. Отчёт по первому заданию лежит в [docs/sre/hw-1/Отчет.md](../hw-1/Отчет.md).

## Состав архива

```
k8s/                      манифесты развёртывания
  kustomization.yaml      точка входа: kubectl apply -k k8s/
  namespace.yaml
  secret.yaml
  postgres.yaml           StatefulSet + Service
  migrate-job.yaml        Job миграций
  backend.yaml            ConfigMap + Deployment + Service
  frontend.yaml           Deployment + Service (NodePort)
backend/Dockerfile        образ lifeboard-backend:0.2.0
frontend/Dockerfile       образ lifeboard-frontend:0.2.0
scripts/start-minikube.sh запуск minikube с рантаймом Docker
scripts/build-images.sh   загрузка базовых образов и сборка в Docker-демоне minikube
backend/, frontend/       исходный код (нужен для сборки образов)
скринкаст                 запись демонстрации
```

## Использованные абстракции Kubernetes

| Абстракция | Где | Зачем |
|---|---|---|
| **Namespace** | `lifeboard` | Всё приложение изолировано в своём пространстве имён. Удаляется одной командой |
| **Secret** | `lifeboard-db` | Логин, пароль и `DATABASE_URL`. Попадают в контейнеры через `envFrom` и `secretKeyRef`, в образах и манифестах подов их нет |
| **ConfigMap** | `backend-config` | Несекретная конфигурация бэкенда: порт, время дренажа при остановке |
| **StatefulSet** | `postgres` | База данных. Стабильное имя пода `postgres-0` и собственный том, который переживает пересоздание пода |
| **PersistentVolumeClaim** | `data-postgres-0` | Создаётся автоматически из `volumeClaimTemplates`. В minikube обслуживается встроенным storage-провайдером |
| **Job** | `migrate` | Разовое применение миграций. Отрабатывает и завершается, а не крутится постоянно |
| **initContainer** | в Job `migrate` | Ждёт, пока Postgres начнёт принимать соединения, и только потом пускает миграции |
| **Deployment** | `backend`, `frontend` | Stateless-сервисы. Управляют ReplicaSet'ами, дают масштабирование и rolling update |
| **ReplicaSet** | создаются Deployment'ами | Поддерживают нужное число реплик |
| **Service ClusterIP** | `postgres`, `backend` | Стабильный DNS-адрес и балансировка между репликами внутри кластера |
| **Service NodePort** | `frontend`, порт 30080 | Единственная точка входа снаружи кластера |
| **Liveness/Readiness probes** | все Deployment'ы и StatefulSet | Перезапуск зависших контейнеров и вывод неготовых подов из балансировки |
| **Startup probe** | `postgres` | Даёт базе до 150 секунд на первый старт с `initdb`, пока liveness не включилась |
| **Kustomize** | `kustomization.yaml` | Все манифесты применяются одной командой, namespace проставляется централизованно |

### Почему Postgres — StatefulSet, а не Deployment

Базе нужны стабильная идентичность и собственный том. Deployment создаёт взаимозаменяемые поды со случайными именами и общим шаблоном тома. StatefulSet даёт поду имя `postgres-0` и закрепляет за ним PVC `data-postgres-0`: если под пересоздать, данные останутся.

Postgres не масштабируется: `replicas: 1`. Репликация Postgres — это отдельная задача с primary/replica и оператором, а не увеличение числа реплик.

### Почему миграции — Job

Если бы миграции запускались при старте каждого пода бэкенда, то при `replicas: 2` и выше несколько подов одновременно пытались бы применить одну и ту же миграцию. Отдельный Job выполняет её ровно один раз. Миграции транзакционные и идемпотентные: учитываются в таблице `schema_migrations`, повторный запуск ничего не ломает.

## Как сервисы взаимодействуют

```
Браузер
  │  http://<minikube ip>:30080
  ▼
Service frontend (NodePort)  ──балансирует──►  Pod frontend × N   (nginx)
                                                 │ /        → статика
                                                 │ /api/*   → proxy_pass http://backend:3000
                                                 ▼
                              Service backend (ClusterIP)  ──балансирует──►  Pod backend × N   (Express)
                                                                               │ DATABASE_URL
                                                                               ▼
                                                       Service postgres (ClusterIP)  ──►  Pod postgres-0
                                                                                            │
                                                                                            ▼
                                                                                   PVC data-postgres-0

Job migrate ──(initContainer ждёт pg_isready)──► Service postgres ──► применяет миграции и завершается
```

- **Браузер → frontend.** Снаружи доступен только NodePort `frontend`. Nginx отдаёт статику и проксирует `/api/*` на бэкенд. Браузер работает с одним origin, CORS не нужен.
- **frontend → backend.** По имени Service `backend`: внутрикластерный DNS резолвит его в `backend.lifeboard.svc.cluster.local`. Адрес передаётся переменной окружения `BACKEND_URL`, в образ не зашит.
- **backend → postgres.** По имени Service `postgres`, строка подключения берётся из Secret.
- **Балансировка.** Каждый Service распределяет запросы между готовыми подами своего Deployment. Под, у которого не проходит readiness probe, в балансировку не попадает.

### Пробы бэкенда

По замечанию к ДЗ №1 проверки разделены:

- **`/livez` — liveness.** Процесс жив и отвечает. В базу не ходит: если база упала, перезапуск подов бэкенда не поможет, а только устроит каскад рестартов.
- **`/readyz` — readiness.** Под готов принимать трафик: база доступна и миграции применены (`SELECT 1 FROM schema_migrations`). Пока Job миграций не отработал, поды бэкенда запущены, но трафик на них не идёт.

### Пробы Postgres

У базы три пробы. Без `startupProbe` liveness убивала Postgres посреди `initdb`: при холодном старте всё запускается одновременно, нода нагружена, и инициализация занимает больше 20 секунд. Теперь у базы есть до 150 секунд на старт, а liveness и readiness включаются только после того, как startup-проба прошла.

### Корректная остановка

По SIGTERM бэкенд сначала начинает отвечать 503 на `/readyz`. Kubernetes выводит под из Service, и новые запросы на него больше не приходят. Через `SHUTDOWN_DRAIN_MS` (5 секунд) процесс дожидается текущих запросов, закрывает пул соединений и выходит. Укладывается в `terminationGracePeriodSeconds: 20`. В `RollingUpdate` выставлено `maxUnavailable: 0` — при обновлении число готовых реплик не проседает.

## Сборка и запуск

```bash
./scripts/start-minikube.sh      # minikube с рантаймом Docker
./scripts/build-images.sh        # minikube image load базовых образов + сборка в демоне minikube
kubectl apply -k k8s/
kubectl -n lifeboard get pods -w
minikube service frontend -n lifeboard
```

**Рантайм Docker обязателен.** В minikube 1.39 по умолчанию стоит containerd, а с ним не работает `eval $(minikube docker-env)`. Поэтому в скрипте старта явно указан `--container-runtime=docker`.

**Как образы попадают в кластер.** Базовые образы (`node`, `nginx`, `postgres`) скачиваются на хосте и загружаются в minikube через `minikube image load`. Образы приложения собираются сразу в Docker-демоне minikube после `eval $(minikube docker-env)`, поэтому в манифестах стоит `imagePullPolicy: Never`: кластер берёт их локально и в реестр не ходит.

## Что выяснилось при развёртывании

- **Liveness убивала базу при первом старте.** Исправлено через `startupProbe`, см. «Пробы Postgres». Проверено холодным стартом с пустым томом: ноль рестартов у всех подов.
- **В логах терялся путь запроса.** Смонтированный роутер Express обрезает `req.url`, а запрос логировался уже после ответа, поэтому все запросы записывались как `/`. Теперь путь запоминается до роутинга. После исправления по логам видно, как Service распределяет запросы между репликами: 40 запросов на 4 пода бэкенда разошлись как 12, 8, 11 и 9.
- **Данные Postgres переживают удаление namespace.** Провайдер хранилища minikube хранит тома в `/tmp/hostpath-provisioner/<namespace>/<pvc>` на ноде и при удалении PVC каталог не чистит. Новый PVC с тем же именем подхватывает старую базу. Для чистого старта: `minikube ssh -- sudo rm -rf /tmp/hostpath-provisioner/lifeboard`.

### Про многопользовательский режим

Продукт проектируется как self-hosted: каждый разворачивает свой экземпляр, и у экземпляра один владелец. Изоляция пользователей обеспечивается изоляцией инсталляций, а не строкой `owner_id` в каждой таблице. Цена решения зафиксирована в [docs/ARCHITECTURE.md](../../ARCHITECTURE.md): переход к нескольким пользователям в одной инсталляции — это миграция схемы, а не флаг.

## Сценарий скринкаста

1. `./scripts/start-minikube.sh` — если кластер уже поднят, достаточно `minikube status`.
2. `./scripts/build-images.sh` — `minikube image load` и сборка образов.
3. `kubectl apply -k k8s/` — создание всех ресурсов.
4. `kubectl -n lifeboard get pods -w` — дождаться, пока Job `migrate` станет `Completed`, а остальные поды — `Running` и `1/1`.
5. `kubectl -n lifeboard get all` — все ресурсы разом.
6. `kubectl -n lifeboard scale deployment backend --replicas=4` и `kubectl -n lifeboard scale deployment frontend --replicas=3`, затем снова `kubectl -n lifeboard get pods`.
7. `minikube service frontend -n lifeboard` — откроется UI. Создать раздел, завести в нём таску, сменить ей статус, удалить.
8. `kubectl -n lifeboard logs -l app=backend --prefix --tail=20` — видно, что запросы из UI обработали разные поды бэкенда.
